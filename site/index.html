The API is a naming convention

Rooms do what their prefix says

No setup calls, no room provisioning. A client subscribes to a room id and the prefix decides its behavior — presence, history, join verification, or any combination.

PrefixBehaviorTypical use
pub-Open fan-out — anyone with a valid connection can join and publish.feeds · tickers · dashboards
pri-Your backend approves every join through a verification webhook.paid channels · org-only rooms
pub-state-Joins and leaves broadcast to the room with the member's metadata.presence · lobbies · "3 people viewing"
pub-cache-Messages are kept — 5 MiB of recent history per room in embedded LMDB, oldest evicted, readable over REST. Optional MySQL archive.chat · comments · activity logs
pri-state-cache-Prefixes compose — verified join, presence, and history together.team chat
Around the socket

Built for the backend you already have

Socketlink handles the connections; your backend stays the source of truth. TLS terminates at your load balancer — inside your network it speaks plain ws://.

Per-user HMAC tokens

Your backend mints a signed token per user at login. Holding the client API key alone is not enough to impersonate anyone.

Webhooks for everything

Message, subscribe, unsubscribe, room-occupied and room-vacated events post to your endpoint, HMAC-signed, off the delivery path.

No cold rooms

A client joining a cache room fetches recent messages in one REST call — newest first, bounded at 5 MiB per room so history can never eat the box.

Ban, mute, broadcast

Admin endpoints ban users from rooms, disable messaging per user, and broadcast to every connection on the server.

MySQL archive

Cache-room traffic can also stream to MySQL on a batched writer thread — retention and search beyond the in-box history window.

One metrics call

Connections, deliveries, drops, sheds, queue depths, memory working set and the live adaptive cap — one JSON endpoint, reconfigurable at runtime.

Overload philosophy

Built to degrade, not to die

Real-time data goes stale in milliseconds, so under overload Socketlink drops the oldest work and keeps the connections — defending its memory budget in explicit stages, each one a counter in /metrics.

at startupHonest cap. The connection limit is computed from the container's memory budget, then re-measured live and shrunk the moment connections get expensive.
slow clientLossy delivery. A subscriber over its backpressure budget loses messages, not its connection — and is told when it's limited and when it recovers.
80% memoryAdmission pause. New connections get 503; existing ones keep running. Resumes at 70%.
still risingShedding. Backpressured sockets — cheapest to lose, most expensive to keep — are closed with "try again later".
queuesByte-bounded everywhere. Webhook and MySQL queues drop oldest past 64 MiB instead of growing until the kernel kills the process.
case file

exit code 139

The stress suite caught the server segfaulting the instant memory-pressure shedding engaged under a full-stack 9.5 KB flood. A gdb backtrace pinned it: closing a slow socket from inside the drop callback freed the exact list node uWebSockets was iterating — a use-after-free deep in topic-tree delivery.

The fix defers the close until after the delivery walk, re-validated by user id so it can never dangle. Six floods out of six now survive with shedding fully active, where every earlier run crashed.

This section exists because a server that claims resilience should show you the crash it earned it from.

Quickstart

Four commands to first message

01Build and run the container

shell
make -j$(nproc)
cp build/socketlink docker/ && docker build -t socketlink docker/
docker run -d --name socketlink --cpus=1 --memory=1g -p 8080:8080 socketlink

02Mint a token in your backend any language with HMAC-SHA256

python
expiry = int(time.time()) + 3600
sig = hmac.new(SECRET, f"{uid}.{expiry}".encode(), hashlib.sha256).hexdigest()
token = f"{expiry}.{sig}"  # hand this to the client at login

03Connect and publish node — browsers connect through your LB, which injects headers

node
const ws = new WebSocket("ws://localhost:8080/", {
  headers: { "api-key": CLIENT_KEY, uid: "alice", token }
});
ws.on("open", () => ws.send(JSON.stringify({ rid: "pub-state-lobby", message: "hello" })));
// subscribers receive {"data":"hello","source":"user","rid":"pub-state-lobby"}

04Read a room's history

curl
curl -H "api-key: $CLIENT_KEY" -H "uid: alice" -H "token: $TOKEN" \
  "http://localhost:8080/api/v1/messages/room/pub-cache-lobby?limit=50"
# → ["newest", "older", ...] newest first
Read this before you adopt it

When it's the wrong tool

A genuine pitch includes the cases it loses. These are design decisions, not roadmap gaps.

✕Guaranteed delivery

Under overload it deliberately drops messages to protect connections and memory. Payments, order flow and job queues belong on Kafka, NATS JetStream, or a real queue.

✕Large payloads

Frames are capped at 10 KB. It moves signals and messages, not files — at ~9.5 KB payloads it becomes bandwidth-bound (~522 MB/s measured on one core).

✕Multi-node clustering

One node, many cores. 4.4 M deliveries/s on 8 cores covers a lot of products, but there is no cross-node room fan-out today.

✕End-to-end encryption

TLS terminates at your load balancer and the server sees plaintext. E2E messaging needs encryption in your clients.
